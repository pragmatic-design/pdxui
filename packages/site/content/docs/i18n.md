# Internationalization

PDX ships a small i18n layer built on signals: switch the locale and every translated string and
formatted number/date on the page updates — no reload, no manual re-render.

## The helpers: `$t`, `$n`, `$d`, `$r`

Four global helpers (auto-imported in `.pdx`, like `$signal`):

```pdx
<h1>{{ $t('dashboard.title') }}</h1>
<p>{{ $t('cart.items', { count: cart().length }) }}</p>   <!-- interpolation -->

<span>{{ $n(price(), { style: 'currency', currency: 'EUR' }) }}</span>  <!-- 1.234,56 € -->
<span>{{ $d(order().createdAt, { dateStyle: 'medium' }) }}</span>        <!-- 5 Jun 2026 -->
<span>{{ $r(order().createdAt) }}</span>                                 <!-- "3 days ago" -->
```

- `$t(key, params?)` — translate a key, with `{ placeholder }` interpolation.
- `$n(value, opts?)` / `$d(value, opts?)` — `Intl`-backed number and date formatting for the active locale.
- `$r(date)` — relative time ("in 2 hours", "yesterday").

They're reactive: when the locale changes, every `$t/$n/$d/$r` in the template re-evaluates.

## Set up locales

Declare them once with the `@i18n` rune (the compiler wires loading + the default), or imperatively:

```pdx
@i18n {
  locales: ['en', 'it', 'de'];
  default: 'en';
}
```

```ts
import { initI18n, loadTranslations, setLocale } from '@pdxui/core';

initI18n({ locale: 'en', fallback: 'en' });
loadTranslations('it', { 'dashboard.title': 'Pannello', 'cart.items': '{count} articoli' });
```

For lazy per-locale loading from files, use `createI18nLoader({ mode: 'static', basePath: '/locales' })`.

Those files are also where `pdx i18n validate` looks: `translations/`, `locales/` and
`public/locales/`, under the source root and the project root, or wherever `--dicts` says.

**Composing a key is fine.** `$t('nav.' + key)` is how you translate an enum, and the tooling reads
the literal part as a prefix: nothing under `nav.` is reported missing, and nothing under it is
reported unused. See [the CLI](/docs/cli) for what the check says and does not say.

## Switch the locale

```ts
import { setLocale, getLocale } from '@pdxui/core';

setLocale('it');           // every $t/$n/$d/$r on the page updates

// getLocale returns the **signal**, not the string — that is what makes it reactive.
const locale = getLocale();
locale();                  // 'it'
getLocale()();             // 'it', in one expression
```

⚠️ **`getLocale()` is not a string**, and a line written as if it were fails somewhere other than
where it was written: passed to something expecting a locale code it throws
`locale.startsWith is not a function`, and if that happens during the app's bootstrap the symptom
is a page that will not mount at all.

In a template the call is the same, and the binding reads the signal for you:

```pdx
<script setup>
import { getLocale } from '@pdxui/core';
const localeSignal = getLocale();
const locale = $derived(localeSignal());     // the string, reactively
</script>

<pdx-select :value="locale" @pdx-change="e => setLocale(e.detail)" :options="locales" />
```

## Translating the built-in components

`$t` covers **your** strings. The library's own — "No items", "Remove", "404 · Page not found",
"Loading..." — live in a **separate registry**, and this is the single most confusable thing on the
page, so it comes with the warning first:

> **Two registries, and `$t` cannot reach the second one.** `$t('router.notFound')` renders the raw
> key. The component strings are read with `getComponentString('router', 'notFound')()` — a signal,
> like `getLocale`, so the second call is the read — and written with
> `setComponentStrings` / `setLocaleStrings`. A lab run shipped `router.notFound` to a 404 page
> exactly this way.

An application installs its overrides once, at startup:

```ts
import { setLocaleStrings } from '@pdxui/core';

setLocaleStrings({
  select:      { placeholder: 'Seleziona…', noResults: 'Nessun risultato' },
  'data-grid': { empty: 'Nessun record', filter: 'Filtra' },
  router:      { notFound: 'Pagina non trovata', backHome: '← Torna alla home' },
});
```

Sixteen namespaces are registered by the components that ship strings — `calendar`, `cascader`,
`data-grid`, `date-picker`, `field-list`, `form`, `form-actions`, `form-template`, `inline-edit`,
`mention`, `router`, `select`, `time-picker`, `transfer`, `tree-select`, `wizard`. `pdx i18n validate`
knows them and reports a `$t` key under one of those prefixes **by name**, instead of counting it as
an ordinary missing translation, because it is almost always this mistake.

| | |
| --- | --- |
| `setLocaleStrings(byComponent)` | the bulk form — what an app calls, once |
| `setComponentStrings(name, strings)` | one component's overrides |
| `getComponentString(name, key, fallback?)` | a **signal**: it follows a later override |
| `getComponentStrings(name)` | the whole merged set for one component, as a signal |
| `registerComponentStrings(name, strings)` | the **defaults** side — what a component calls for its own English. Your own components use this |
| `clearComponentStrings()` | drops the overrides. For tests |

The two sides are kept in two maps and never merged, so a component imported *after* your
`setLocaleStrings` cannot put its English back by registering its defaults late.

## Reacting to a locale change

Inside a template, `$t` re-renders itself. Outside one — a chart's axis labels, a `document.title`,
anything you build imperatively — subscribe:

```ts
import { onLocaleChange, getSupportedLocales } from '@pdxui/core';
import { isLocaleLoaded, getTranslation, setFallbackLocale } from '@pdxui/core/i18n';

const stop = onLocaleChange(() => redrawAxisLabels());

getSupportedLocales();          // ['en', 'it', 'ar'] — what initI18n was given
isLocaleLoaded('it');           // false until its dictionary has arrived
getTranslation('cart.empty');   // the raw lookup, undefined if absent — no fallback, no key echo
setFallbackLocale('en');        // where a missing key looks next
```

> Three of those come from `@pdxui/core/i18n` and not from the barrel. The
> [API reference](/docs/api) prints the specifier that works for every export, and a symbol reachable
> only from a sub-path is shown with it.

`getTranslation` is the one to be careful with: unlike `$t` it does **not** fall back and does not
echo the key, so `undefined` means "this key does not exist in this locale" — which is what makes it
useful for deciding, and wrong for rendering.

`formatMessage(message, params)` applies the ICU placeholders to a string you already have, and
`validateIcu(message)` returns the syntax error in an ICU string or `null` — the same check
`pdx i18n validate` runs, available to your own build.

## Right-to-left

`setDirection('rtl')` sets the document's direction; `direction` and `isRTL` are signals that follow
it. CSS logical properties handle most of a layout by themselves — `margin-inline-start` rather than
`margin-left` — and the four helpers are for what CSS cannot reach:

```ts
import { inlineStart, inlineEnd, flipPlacement, rtlTransformX } from '@pdxui/core';

inlineStart();                  // 'left' in LTR, 'right' in RTL
flipPlacement('bottom-start');  // 'bottom-end' in RTL
rtlTransformX(12);              // -12 in RTL
```

Reach for them where a value has to be computed rather than declared: a floating element's placement
(see [Building an overlay](/docs/overlays)), a transform in JavaScript, a canvas or an SVG coordinate.
Everything a stylesheet can express should stay in the stylesheet, as a logical property.

## Gotchas

- **Missing keys fall back.** An unknown key resolves to the fallback locale, then to the key string
  itself — so a typo shows the key, not a crash. Watch the console in dev.
- **Format, don't concatenate.** Build `"{count} items"` as one translation with a placeholder, not
  `$t('items') + count` — word order and pluralization differ per language.
- **Currency/locale are separate.** `$n(x, { style:'currency', currency:'EUR' })` formats *with the
  active locale's conventions* but the currency you pass — locale decides the separators and symbol
  position, you decide the currency.
