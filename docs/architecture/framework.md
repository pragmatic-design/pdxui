# PDX UI

## What it is

PDX UI is a complete frontend framework for building web applications. The project comes out of the same philosophy as the Pragmatic backend (.NET): **the developer declares what they want, and the tooling generates the code that takes**. On the backend that happens through C# Source Generators; on the frontend, through a custom compiler that turns `.pdx` files (Single File Components) into standard Web Components.

The result is a framework where writing a component takes a few declarative lines, while the generated code is as optimised as if it had been written by hand.

## Why a framework of our own

Building a framework instead of using React/Vue/Svelte comes down to three things:

1. **Complete control of the pipeline**: we own the compiler, the runtime, the design system and the components. When a feature is needed, we implement it in the right layer — we do not work around somebody else's limits.

2. **Integration with the Pragmatic backend**: the types generated by the .NET Source Generator can feed forms, validation, routing and permissions in the frontend directly. No adapter layer.

3. **Standard Web Components**: the output is the browser's own Custom Elements, usable in any framework or in none. We do not tie the user to our ecosystem.

## How it is organised

The project is a monorepo of 6 packages, each with one precise responsibility:

```
ui-framework/
└── packages/
    ├── core/         @pdxui/core         The runtime: reactivity, templates, components
    ├── compiler/     @pdxui/compiler      The Vite plugin that compiles .pdx → JS
    ├── ui/           @pdxui/ui            50+ ready-made components (button, dialog, rating...)
    ├── design/       @pdxui/design        CSS: tokens, themes, surfaces, layout
    ├── responsive/   @pdxui/responsive    Layout validation, design scoring
    └── framework/    @pdxui/framework     A meta-package: install everything with one import
```

The relationship between the packages is linear:

- **design** provides the CSS tokens and the themes (it has no JS dependencies)
- **core** provides the runtime (signals, the template engine, the Web Component base class)
- **compiler** transforms the .pdx files using what it knows about core
- **ui** builds components on top of core + design
- **framework** re-exports everything, for convenience

## The central idea: .pdx files

A `.pdx` file is a Single File Component (like a `.vue` or a `.svelte`) with three sections:

```html
<template>
  <div class="counter">
    <button @click="increment">Count: ${count}</button>
  </div>
</template>

<script setup>
@page '/demo/counter';
@title 'Counter Example';

let count = $signal(0);

function increment() {
  count++;
}
</script>

<style scoped>
.counter { padding: var(--pdx-space-md); }
</style>
```

The compiler turns this into a JS module that registers a Web Component through `component()` from `@pdxui/core`. The main transformations are:

- `let count = $signal(0)` → creates a reactive signal named `__count`
- `count++` → `__count.set(v => v + 1)` (mutations are rewritten automatically)
- `@page '/demo/counter'` → an entry in the router manifest
- `<style scoped>` → CSS with a `[data-pdx-HASH]` attribute for isolation
- `<button @click="increment">` → an event binding to `ctx.increment`

The developer never writes boilerplate: no manual imports, no `return {}`, no wiring. If they are writing repetitive code, that is a bug in the framework.

## Two modes: development and production

The framework runs in two distinct modes, and that is a deliberate choice:

**Development** — everything interpreted. `pdx dev` starts Vite with HMR. The `.pdx` files are compiled on the fly, bindings are resolved at runtime, validations are active, warnings appear in the console. The goal is instant feedback: save the file, see the result.

**Production** — compilation with global knowledge. `pdx build` sees the whole project: it knows which routes exist, which components are used, which signals are read. That allows optimizations no generic bundler can make:

| Aspect | Dev (interpreted) | Prod (compiled) | Status |
|---------|-------------------|------------------|--------|
| Router | Regex matching at runtime | A generated switch statement | ✅ The build swaps `packages/router/src/active.ts` for the generated router. "Zero regex" holds while no route declares a constraint |
| Bindings | `setProp()` with dispatch | Direct property assignment, inline | ✅ The default of a production build. Mount of a 1500-row list: 19 ms → 5.5 ms, +0.4 KB raw, 0 KB gzip. `pdx({ inlineBindings: false })` turns it off |
| Template | `html\`\`` with reactive placeholders | A pre-compiled DOM factory | ⚠️ Only for a template with no interpolation |
| CSS | Scoping through a data attribute at runtime | CSS extracted, zero JS overhead | ✅ A production build imports each component's styles as a stylesheet the bundler extracts. Dev keeps the injection: it is what makes a `<style scoped>` hot-reload |
| Signals | A Proxy with dependency tracking | — | ❌ Retired. Profiled on the showcase's densest screen, the reactive runtime is ~4% of mount time: inlining it could win a fraction of that |
| Validation | Active checks with warnings | Removed | ✅ Diagnostics sit behind a `DEV` constant the bundler folds away. What stays is failures — an unhandled error, a loader that did not answer |

Every row is measured, not asserted: `packages/showcase/tests/compiler-claims.spec.ts` compiles
the showcase in production mode and reads the bundle.

## Architectural choices

### Light DOM instead of Shadow DOM

A Web Component can use the Shadow DOM (an isolated DOM with native scoping) or the Light DOM (a DOM visible in the main tree). We chose the Light DOM for three reasons:

- **CSS token pass-through**: the CSS tokens (`var(--pdx-color-primary)`) work naturally, without having to "pierce" the shadow boundary. Themes simply work.
- **Readable DevTools**: the DOM tree in the browser's tools shows every element, with no shadow roots to expand.
- **Simple slot projection**: the Light DOM makes composing nested components enormously simpler.

CSS scoping — normally what the Shadow DOM guarantees — is handled by the compiler, which adds a `[data-pdx-HASH]` attribute to every selector; the same approach Vue takes.

### Signal-based instead of a Virtual DOM

Frameworks like React use a Virtual DOM: on every state change they recompute the whole virtual tree and apply the differences to the real DOM. That is conceptually simple and computationally expensive.

Pragmatic uses **signal-based reactivity**: every binding in a template is a micro-effect (`effect()`) that watches only the signals it reads. When a signal changes, only the bindings that read it update — O(1) per binding, not O(n) over the whole tree.

The signal engine is implemented in-house (~6KB gzip), inspired by Preact Signals and SolidJS, with auto-batching and glitch-free updates (no inconsistent intermediate value).

### Zero external dependencies

The core has no npm dependencies. The signal engine, the template engine, the router, the HTTP client, form validation — all of it is implemented in-house. That buys:

- Total control over the bundle size (~25KB gzip for a typical app)
- No risk of a breaking change arriving from a third-party dependency
- Predictable, measurable performance

### Standard Web Components

Every component's output is a Custom Element registered with `customElements.define()`. That means Pragmatic components work anywhere: inside a React, Vue or Angular app, or in an HTML page with no framework at all. The only requirement is a modern browser.

## Adoption levels

The framework is designed to be adopted gradually:

| Level | Scenario | How |
|---------|----------|------|
| 1 | A quick prototype | A script tag from a CDN, zero configuration |
| 2 | A small project | `npm i @pdxui/framework` — everything included |
| 3 | A structured app | Selective imports: `@pdxui/core`, `@pdxui/ui` |
| 4 | Enterprise | The full CLI, tree-shaking, source generation, CI/CD |

## Current state (April 2026)

The framework has reached maturity in these areas:

- **CLI**: the `build`, `dev`, `check`, `new` and `analyze` commands
- **Router**: file-based through `@page`, lazy loading, keepAlive, scroll restoration
- **Data layer**: `@fetch` → `resource()` with cache, mutation, offline
- **Form engine**: `@form` with inline or external validation, field arrays
- **Store**: `@store` singletons with localStorage/sessionStorage persistence
- **Testing**: the `mount()`, `tick()`, `fireEvent()` and `waitFor()` utilities
- **Lifecycle**: 11 hooks (onMount, onDestroy, onVisible, onResize, ...)
- **UI library**: 50+ components (dialog, tabs, rating, segmented, data-source, ...)
- **Design system**: 9 themes (Default, Material, Fluent, Cupertino, ...), dark mode, density
- **DevTools**: an inspector overlay + a signal inspector

Still in development: i18n, touch/mobile, image optimization, an LSP for IDEs, SSR/SSG.
